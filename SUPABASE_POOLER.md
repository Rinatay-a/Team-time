# Развёртывание базы через IPv4 Session Pooler

## Что исправлено

В запуске `39118187450` CLI **2.121.0** завершил `link`, затем остановился на IPv6 **до запуска миграций**. По этому журналу нельзя определить, были ли таблицы созданы вручную или другим запуском.

В исходниках этой версии CLI получение pooler-конфигурации при `link` выполняется как best-effort: ошибки подавляются, поэтому `Finished supabase link` не подтверждает доступность pooler. Следующий `db push` может попытаться использовать прямой IPv6-адрес. Endpoint Management API для pooler требует `database:read` / `database_pooling_config_read`; обычного доступа к проекту недостаточно.

Теперь workflow использует официальный host из Management API и **явно передаёт `--db-url`** всем командам миграций. Порт всегда **5432, Session Pooler**. Прямое соединение и Transaction Pooler 6543 отклоняются. Платный IPv4 Add-on не нужен. Версия CLI остаётся закреплена на 2.121.0; работа больше не зависит от кеша `supabase link`.

## Сначала диагностика без изменения базы

После обновления workflow автоматически запускается в режиме **inspect-database**. Он:

1. Проверяет ответ pooler Management API и выводит только HTTP-статус, без тела и реквизитов.
2. Проверяет наличие IPv4 A-адреса Session Pooler.
3. Через PostgreSQL client с IPv4 и TLS читает только метаданные таблиц, RLS, функций и `supabase_migrations.schema_migrations`.
4. Показывает применённые и ожидающие версии 001/002/003 в журнале и **Summary**. SQL-миграции и Edge Function при этом не развёртываются.

Если схема есть, но история пуста, либо история расходится со схемой, workflow остановится. Он не повторяет 001, не удаляет таблицы и не делает `migration repair` автоматически. В этом случае передайте в чат текст диагностической ошибки и номера миграций из Summary, без строк подключения. Сначала нужно сверить реально выполненный SQL.

## Если API pooler возвращает 401/403 или не даёт адрес

Расширять права токена ради получения адреса базы необязательно. Можно передать адрес из Dashboard отдельно; `SUPABASE_ACCESS_TOKEN` останется для публикации функции.

1. Supabase Dashboard → ваш проект → кнопка **Connect**.
2. Откройте **Connection String**, формат **URI**, Method — **Session pooler**. В некоторых версиях интерфейса раздел называется **Session pooler → Connection parameters**.
3. Убедитесь, что host заканчивается на `.pooler.supabase.com` и порт **5432**. Не выбирайте **Direct connection** или **Transaction pooler** (6543). Используйте адрес именно вашего проекта/региона, не угадывайте его.
4. Скопируйте URI. Если он содержит `:[YOUR-PASSWORD]`, удалите **весь этот фрагмент**, включая двоеточие перед квадратной скобкой. Оставьте пользователя `postgres.<ваш project ref>` перед `@`. Пароль уже сохранён в `SUPABASE_DB_PASSWORD`, helper добавит его безопасно и выполнит URL-кодирование.
5. Получится строка такой структуры (не копируйте шаблон вместо вашего адреса):

   `postgresql://postgres.PROJECT_REF@POOLER_HOST:5432/postgres?sslmode=require`

6. GitHub → **Rinatay-a/Team-time → Settings → Secrets and variables → Actions → Secrets → New repository secret**.
7. Имя: **SUPABASE_DB_URL**. Значение: подготовленный URI Session Pooler. Нажмите **Add secret**. Это не `VITE_`-настройка и не ключ API.

Можно сохранить URI с уже URL-кодированным паролем, но вариант без пароля использует существующий Secret и позволяет избежать ошибок со спецсимволами. Сам пароль и полную строку не отправляйте в чат. Значение Secret недоступно для чтения Codex и не записывается в исходники.

## Запустить проверку и миграции

1. Откройте [Развёртывание Supabase](https://github.com/Rinatay-a/Team-time/actions/workflows/supabase.yml).
2. **Run workflow**, ветка **main**, операция **inspect-database** → **Run workflow**. Это проверит новые настройки без применения SQL.
3. Если показано `Применено: нет. Ожидает: 001, 002, 003`, база пуста и готова к первоначальному развёртыванию. Если уже есть последовательность 001 или 001/002, будут применены только оставшиеся версии. Если все три применены, повторного SQL не будет.
4. После успешной проверки снова **Run workflow → main → migrations-and-function → Run workflow**. Не используйте **Re-run jobs** старого запуска: он использует старую версию workflow.
5. Новый запуск повторно прочитает историю, выполнит `migration list`, `db push --dry-run`, снова проверит историю, затем применит только ожидающие миграции и проверит схему после них.
6. После этого опубликуется `team-time-api`. Отдельная проверка Management API подтвердит **ACTIVE** и **verify_jwt=false**. Секрет пароля базы передаётся только шагу БД.

Итог в журнале/Summary: применены **001, 002, 003**, существуют **6 таблиц с RLS**, функция **team-time-api ACTIVE**. В Supabase это также видно в **Table Editor** и **Edge Functions**. Содержимое ответов workflow не читает.

## Когда нужна помощь

- **Pooler API HTTP 403**: недостаточный доступ к pooler-настройкам; используйте `SUPABASE_DB_URL` выше. Для scoped OAuth это `database:read`; для PAT доступ ограничен ролью владельца токена в организации/проекте. Не выдавайте Owner/Admin только ради этого чтения.
- **Password authentication failed**: проверьте `SUPABASE_DB_PASSWORD` (пароль БД, а не пароль входа организатора) и пользователя `postgres.<PROJECT_REF>`.
- **Нет IPv4**: в URI указан неправильный host либо выбран Direct connection.
- **Схема без истории / история расходится**: не запускайте SQL Editor или repair наугад; сначала сверим миграции. Три исходных файла миграций в этом исправлении не меняются.
- **Ошибка публикации функции 401/403**: это отдельная проверка доступа токена к Edge Functions; URL базы её не исправляет.
