# Подготовить GitHub Pages и безопасный запуск Supabase

Приложение работало в демо, но публикационный workflow отсутствовал, базовый путь не соответствовал `Team-time`, а реальное сохранение падало из-за неоднозначного `participant_id` в SQL-функции. Исправление сохраняет текущий дизайн и архитектуру и готовит запуск с общей базой Supabase.

- Добавлены проверки CI и публикация GitHub Pages из `main` с `/Team-time/` и выключенным демо.
- Production-сборка требует публичную конфигурацию и отвергает секретные ключи.
- Добавлена миграция 003 без изменения 001/002: исправление сохранения, точная проверка версии, защита от гонки с закрытием опроса и повтором первого сохранения.
- Исправлен разбор HTTP 409 и проверка ошибок административных изменений. Настройки Edge Function перенесены в корневой `supabase/config.toml`.
- Добавлены ручной workflow Supabase, проверка подключения без записи и инструкция DEPLOYMENT.md.

Проверено: lint, 48 тестов (включая PostgreSQL/RLS и HTTP API), deno check, production build, 5 браузерных сценариев, npm audit и audit --omit=dev (0 уязвимостей). Детали и границы проверки: VERIFICATION.md.

Перед реальным запуском владельцу нужно настроить Supabase, создать организатора, применить миграции, опубликовать функцию, задать публичные GitHub Variables и включить Pages. Облачный Supabase и опубликованный сайт пока не проверены; тесты браузера подменяют HTTP API. После слияния публикация остановится, если Variables ещё не заполнены.
